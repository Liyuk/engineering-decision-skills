# 一线工程分析与决策 Skills：设计说明

## 用户意图

作者认可现有五项能力，想让一线工程工作者可以直接使用它们，协助分析和决策。项目不需要扩成覆盖招聘、绩效、1:1、个人发展、团队士气等主题的全面工程管理助手。沟通材料只在它能承载已有分析结论、帮助相关读者作决定时出现。

## 目标用户与要完成的工作

目标用户是工程师、技术负责人、项目/产品协作者等处在具体交付和决策现场的人。他们提供已有的方案、计划、指标、过程记录或项目事实，希望更清楚地知道：

1. 有限工程能力应该投到哪里，什么暂缓或停止；
2. 一个数字到底测量什么，变化是否可信；
3. 现有技术方案是否有足够证据和交付保障支持决定；
4. 已完成的工作能支持什么学习，下一次改什么；
5. 怎样把上述已形成的信息整理成读者可判断、可行动的材料。

## 产品主张

五项独立的辅助分析与辅助决策工作流，帮助用户把提供的信息整理成可检查的判断：明确任务和决策、保留事实来源与状态、显露关键取舍和未知、只给证据支持的结论，并提供可验证的下一步。它们不替代数据访问、领域专家审查、组织决策权或人的判断。

项目的内容来源于作者个人写作和经验，但“源自个人经验”不是独有竞争优势。可验证的产品假设是：在具体工程决策任务里，这些技能能比通用回答更稳定地保留信息来源/未知状态、匹配任务并给出适量且可执行的下一步。该假设须持续用评测和真实用户案例验证，不作为已证实的效果宣传。

## 五项技能的边界

| Skill | 面向的工作判断 | 不扩成 |
| --- | --- | --- |
| `tech-planning` | 约束下的工程投资、优先级、暂缓/停止、路线图与验证门 | 通用产品战略、自动市场研究、实施任务拆解 |
| `metric-decision` | 指标定义、测量有效性、变化解释边界和下一步行动 | 自动数据分析、个人生产力打分、通用指标仪表盘 |
| `tech-review` | 对已有方案作有证据边界的决策就绪评审 | 自动改写方案、替代安全/隐私/合规等专项审查 |
| `management-retro` | 从已完成工程工作中识别有依据的系统模式并选取下一次改进 | 员工绩效/情绪诊断、团队健康顾问、强制流程设计 |
| `eng-reporting` | 把用户已提供或已确认的结论组织成目标读者可用的简明材料 | 泛沟通教练、替用户创作事实、独立进行复盘分析 |

它们互补但不构成必须依次运行的漏斗。只调用当前任务所需的技能；只有输入/输出真正跨越工作边界时才组合。

## 共用质量约定

- 明确区分用户提供事实、来源事实、测量、估算、推断、假设和未知；需要时保留来源、口径、时间范围。
- 信息不足时，说明缺少什么以及计算/核实口径。只有会改变核心判断的缺失信息才阻断输出。
- 冲突信息先按来源与口径并列，不擅自挑选、平均或构造根因。
- 只给证据支持的结论；评审可在没有阻塞问题时通过，复盘可结论为尚不能确认系统性原因。
- 输出匹配任务、读者和风险；不为完整感强制填满模板、指标、负责人或日期。
- 建议动作应有可检查的验证方式；负责人和时间未知时明确待确认。

## 社区参考结论

`manager-dot-dev/manager-skills` 是直接的工程管理领域参照。其路线图、生产力、业务沟通、复盘等技能与部分本项目场景重叠；它展示了短触发、有限追问、结论先行和可执行下一步等交互方式值得借鉴。复制它的人员管理、员工上下文记忆、团队健康和广泛沟通能力会改变产品范围并引入敏感个人数据问题。Matt/Han 更适合作为工程交付、计划与评审边界参照。以上为公开仓库意图比较，不代表对方效果已获实证。

## 验收标准

1. README 首屏用一段话说明目标用户、辅助分析/决策价值和五项调用场景；不将项目定位成全能管理助手。
2. 五项技能均可从独立入口理解触发条件、输出和边界，且 `eng-reporting` 明确依赖已有材料/结论。
3. 保留作者原文映射及管理复盘八个判断的来源结构；竞争对比不抹去个人写作来源，只说明它本身不构成独特性。
4. 所有项目说明和博客草稿中的技能数量、用例数、评测样本和限制均与仓库当前状态相符。
5. 每项技能至少有缺数据、冲突信息和正常任务的行为用例；评分继续采用事实克制、任务匹配、可执行性、格式、语气五个维度。
6. `python3 scripts/validate_repo.py` 与 `git diff --check` 通过；评测结论不得被写成跨模型或真实业务效果证明。

## 风险与限制

- 本地 prompt 评测为小样本人工行为检查，不能证明用户采用或组织收益。
- “一线人员”是产品受众定位，不表示所有五项都只面向个人 IC；例如规划与复盘仍会由技术负责人使用。
