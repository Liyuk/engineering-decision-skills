# 技术方案评审方法：一手来源与适用边界

> 历史调研记录。面向使用者的当前方法参考见 [`tech-review 方法来源与边界`](../../../skills/tech-review/references/method-sources.md)；下文保留调研时的来源快照，不作为当前引用入口。

- **调研日期：** 2026-09-25
- **问题：** `$tech-review` 是否应支持逐项核对、证据关联发现、检查清单、无阻塞时通过、评审范围规划和风险优先级？这些做法应如何引用来源？

## 摘要

一手来源支持采用**有范围的检查清单、明确评审准入/完成条件、记录发现并跟进、把技术意见与依据和影响关联、按风险确定评审重点**。它们不支持把每个章节都强行批判一遍，也不能证明某个 AI skill 的输出有效。

建议 `$tech-review` 提供两种清晰模式：

1. **决策评审（默认）**：检查与当前决策相关的主张、风险和证据；只报告有材料支持且会改变判断或交付的发现；没有阻塞问题时允许通过。
2. **逐项覆盖（按需）**：按用户提供的章节、需求、选项或设计决策逐项标记“支持充分 / 有缺口 / 信息冲突 / 待确认 / 不适用”，并在清单末尾列出有实质影响的发现。覆盖每项不等于每项都要批判。

逐项模式应注明审查边界（材料、章节/条目范围、目标和决策）及未检查部分。若无具体条目清单，可先从材料中提取目录或主张作为覆盖表，并将其标为评审者整理的范围，而非原文已有的完整需求追溯矩阵。

不需要把学术论文写进每次面向用户的评审答复。仓库可以保留一个简短的“方法来源”参考页，skill 本身只链接它；用户要求方法依据或正式评审时再展开引用。NASA 规范、正式检查方法和 Google 代码评审实践有各自适用场景，不能包装成所有工程提案的强制标准。

## 来源及可支持的主张

### 1. NASA 软件同行评审要求：计划、清单、完成准则和跟进行动

NASA《NPR 7150.2B》将同行评审和检查定义为生命周期内由同行对工作产品开展的技术检查，以尽早发现和消除缺陷；流程需涵盖准备、实施、记录和报告结果，以及确认完成准则。对计划中的评审/检查，它要求使用清单或正式阅读技术、建立就绪和完成准则、跟踪行动直至解决，并识别所需参与者。[NASA NPR 7150.2B, §§5.3.1–5.3.4](https://swehb.nasa.gov/download/attachments/16450392/N_PR_7150_002B_.pdf?api=v2)

**可用于本 skill 的窄结论：**逐项覆盖可以作为用户选择的阅读方法；检查清单应按材料和风险定制，且用“不适用”避免机械套用；评审前定义范围/完成条件，评审后记录行动状态有一手依据。

**边界：**这是 NASA 的软件工程要求，面向其项目治理，不应写成一般团队或个人使用此 skill 的合规义务。该文档覆盖需求、计划、设计项、代码、测试程序，不等于所有技术提案都必须经过正式审查。

### 2. NASA 系统工程验证指南：发现须记录依据并可追踪

NASA 产品验证指南将 discrepancy 描述为与要求或预期结果不一致的偏差、缺少一致性或矛盾；建议记录差异、跟进关闭，并记录验证结果、决定、理由、假设和纠正行动。其验证报告还包括所验证要求、追溯关系、方法、结果和异常。[NASA Systems Engineering Handbook, §5.3](https://www.nasa.gov/reference/5-3-product-verification/)

**可用于本 skill 的窄结论：**评审发现要指明被评审的主张/要求或材料位置、支持依据、影响和后续动作；待验证内容与已证实缺陷应分开；决定及理由要能追溯。

**边界：**验证产品是否满足已定义要求与评估提案是否适合某一投资决策不是同一任务。可借鉴可追溯记录方式，不可声称该指南直接规定提案评审必须采用某个输出字段或 pass 标准。

### 3. Fagan 1976：正式检查是有目标和阶段准则的流程

Fagan 的 IBM Systems Journal 论文讨论设计和代码检查，建议将开发流程分解为操作并定义退出准则；将准备、检查、返工和跟进的目标区分开；分类错误并集中检查常见类型；分析检查结果以改进流程。[Fagan, “Design and code inspections to reduce errors in program development,” IBM Systems Journal 15(3), 1976, pp. 182–211](https://doi.org/10.1147/sj.153.0182)（[可读论文副本](https://www.ida.liu.se/~TDDC90/labs/lab-papers/fagan76.pdf)）

**可用于本 skill 的窄结论：**先确定本轮评审要回答的决策问题；清单服务于集中注意，不是穷尽式找茬；审查发现和提出修改是不同阶段，除非用户同时要求评审与改写。

**边界：**论文主要研究正式设计/代码检查流程，不是 AI 文档评审实验。论文中的质量或生产率结论不能外推为本 skill 有效性的证据。

### 4. Gerrit 设计文档流程：评估选项并记录决定理由

Gerrit 的设计文档规范建议写明用例、验收条件、背景、可能方案及优缺点、实现细节和最终决定/理由；不同方案应公平讨论，达成结论后继续维护文档以记录实现阶段的新信息。[Gerrit Code Review: Design Docs](https://gerrit-review.googlesource.com/Documentation/dev-design-docs.html)

**可用于本 skill 的窄结论：**检查方案是否从问题/用例连接到可接受条件、备选方案、取舍和决策理由；如果没有备选方案或理由，应判断它是否影响当前决策，而不是单凭缺一节判为缺陷。

**边界：**这是 Gerrit 社区自己的设计提案协作流程，建议按场景借鉴，不是跨组织通用规范。

### 5. Google 工程实践：逐行审查只适用于明确的代码变更范围

Google 的代码评审指南要求审查被分配的代码行和上下文，同时看设计、功能、复杂度、测试、文档等；若评审者只被指派特定文件或特定方面，应说明实际覆盖范围。它还建议事实与数据优先于个人偏好，并用标记区分必需修改和可选建议。[Google: What to look for in a code review](https://google.github.io/eng-practices/review/reviewer/looking-for.html)、[How to write code review comments](https://google.github.io/eng-practices/review/reviewer/comments.html)、[The Standard of Code Review](https://google.github.io/eng-practices/review/reviewer/standard.html)

**可用于本 skill 的窄结论：**“逐条批判”应先被澄清为覆盖范围要求，而非保证每条都存在问题；标明未评审范围；将阻塞决策的问题和非阻塞建议分开；不把个人偏好写成缺陷。

**边界：**Google 页面规范的是代码变更评审，不是技术立项或架构提案审查。它可支持审查纪律和评论语气，不能直接支持提案结论等级。

### 6. Google Cloud 重大变更流程：评审深度随风险和变更影响而变

Google Cloud 描述的重大变更流程会由资深专家、可靠性和安全专家等综合评审方案；方案需讨论业务、技术、成本和维护要求，反馈处理并获批准后才进入实现。[Google Cloud: Our approach to change](https://docs.cloud.google.com/docs/cloud-approach-to-change)

**可用于本 skill 的窄结论：**高影响、跨系统、安全或可靠性相关提案可以提高检查深度，必要时指出应由相应领域专家复核。评审重点可根据潜在后果、方案不确定性和证据缺口调整。

**边界：**该页面介绍 Google Cloud 内部的重大变更程序，且主要面向重大生产变更；不能据此要求所有小型方案走同样审批链。公开材料也没有给通用的 P0/P1 严重度标尺。

### 7. ADR：架构决策应保留关键选项、约束和选择理由

Google Cloud 的 ADR 指南描述了 ADR 对关键备选项、驱动决策的要求和设计决定的记录作用；典型内容包括问题背景、功能/非功能要求、关键选项、决定及其原因。[Google Cloud Architecture Center: Architecture decision records](https://docs.cloud.google.com/architecture/architecture-decision-records)

**可用于本 skill 的窄结论：**评审架构或技术选型时，核对目标/约束、备选项、取舍和选择理由；若材料只证明“能实现”却没有证明“适合当前约束”，评审可以提出证据缺口。

**边界：**ADR 是决策记录格式，不是评审流程或证明某决定正确的方法。

## 对逐条评审问题的直接回答

“逐条批判”有两种含义，技能应区分：

- **要求逐项覆盖：可以支持。**对一组明确条目做覆盖表，标明充分、缺口、冲突、待确认或不适用。NASA 的清单/正式阅读技术要求和 Google 对代码评审范围的明确说明支持这种覆盖纪律。
- **要求每项都批判：不应默认支持。**来源强调发现实际差异/缺陷、尊重评审目标和事实依据，并区分可选建议；不要求为每一项制造负面评论。覆盖项“支持充分”或“未发现实质问题”是有效结果。
- **逐条定位原文：建议仅在材料结构支持时启用。**评审者应链接章节、需求编号、表格行或引用短句。若材料没有稳定编号，可用标题/段落定位并说明定位近似；不要伪造追溯关系。

## 对 `$tech-review` 的具体设计建议

1. **默认按决策风险进行相关性检查**，保留现有架构、迁移、兼容、安全、容量、测试、可观测性、发布、回滚和运维检查清单；清单只提示关注点，允许跳过不适用项。
2. **增加显式的覆盖模式**：用户说“逐条/逐章节/对照需求检查”时，先建立条目清单，按状态覆盖全部条目，再单独汇总实质发现。用户要求仅审某章节或某维度时，注明范围和未覆盖部分。
3. **区分覆盖状态和问题严重度**。覆盖状态表示审查进度/证据状态；严重度表示发现对决策/交付的后果。二者不要复用一个标签。
4. **发现保留证据链**：材料位置或来源 → 被质疑的主张/要求 → 依据或缺失输入 → 决策/交付影响 → 建议动作与状态。缺数据标待确认；有冲突就列出两方材料及冲突本身；未知不能伪装成否定结论。
5. **按后果定义优先级，避免虚假的精确分数**。优先级应解释是否阻止当前决策、是否会造成重大质量/安全/数据/客户影响，还是仅供改进；风险高但证据不确定时，应把“后果严重”和“发生可能性未知”分别说清。现有仓库优先级字段可沿用，不必借未经来源支持的通用数字刻度。
6. **允许“通过/无阻塞”**，但把它限定为：“在声明的范围及已提供材料内，没有找到足以阻止当前决策的有依据问题。”附上未验证的关键假设或未覆盖范围。NASA/Google 的程序来源支持记录结果、结论与范围，但公开来源并没有为一般 AI 技术方案评审规定统一的 pass 标签；这是为本 skill 设计的适用输出。
7. **把评审和方案重写分开**。正式检查中的发现与返工/修复是分开的过程；输出可以建议动作，但除非用户明确要求，不直接替作者改写提案。

## 学术来源是否必要

**对用户可见的 skill 使用说明，不需要放一串论文。**可在单独的 `references/method-sources.md` 放 4–6 条精选的权威来源，并在 skill 文末用一句话链接：“本方法参考正式软件评审、设计文档评审和代码评审实践；这些来源是方法参考，不构成本项目有效性证明。”这样既可追溯，也不把独立 skill 的入口变成长文。

最有用的少量来源组合：

- NASA NPR 7150.2B：正式评审的清单、准入/完成条件、行动跟踪。
- Fagan 1976：检查流程与发现/返工/跟进目标分开。
- Gerrit Design Docs：用例、验收条件、备选方案、优缺点和决策理由。
- Google Code Review：限定审查范围、事实高于偏好、必需与可选意见区分（明确其仅是代码评审类比）。
- Google Cloud design/ADR 文档：重大变更风险评审及决策记录。

论文适合支撑“正式检查流程曾被描述/研究”这类背景，但本 skill 的逐项覆盖、无阻塞通过等行为规范，直接引用 NASA 与一线项目官方流程通常更合适。若未来要声称“使用此 skill 提升决策质量/减少缺陷”，必须另做用户研究或对照评测；上述文献并不验证该产品效果。

## 来源范围限制

- 这些来源来自航天软件、代码评审、设计文档和架构决策记录，行业/任务背景不同。
- 它们提供的是评审流程和记录实践，不是基于实验的 AI skill 效果证明。
- “有来源支持检查清单和记录结论”不等于“通用清单对所有提案都有效”。技能必须保留任务匹配、可跳过项和范围说明。
- 本说明没有建立适用于所有项目的风险概率/影响评分公式。风险标签应明确成项目决策辅助语义，而不要冒称行业统一等级。
