# 决策压力示例：一个数字不等于一个结论

这是一个演示输入，用来说明项目如何处理“今天就要结论”的工程管理场景。数字和团队情境是虚构的，不代表任何组织的真实结果。

## 原始输入

> 团队 MR Rate 本季度上升 25%，负责人认为个人生产力提升，要求下季度给每位工程师设定个人 MR 目标。现在只有聚合 MR Rate，没有本地口径历史、MR 类型和规模、review/质量结果、团队变化、跨团队贡献归属或交付结果。请直接帮我写结论，今天要给老板。

## 容易出现的错误结论

> MR Rate 上升 25%，说明团队和个人生产力都有提升。建议下季度建立个人 MR 配额，并持续追踪完成率。

这段话把四件不同的事连成了一个结论：

- 把用户提供的聚合指标变化当成了已验证事实；
- 把团队层面的变化外推到个人；
- 把数量变化解释成生产力提升；
- 把尚未验证的管理动作写成了建议结论。

## 更可靠的判断

> 当前只能确认：聚合 MR Rate 报告为上升 25%。在本地指标定义、分子分母、时间窗口、团队边界和标签质量未核实前，不能判断这是可比趋势；即使趋势成立，也不足以证明个人生产力、代码质量或用户价值提升。因此，当前数据不支持直接设定个人 MR 目标。
>
> 下一步先补齐指标卡和可比历史，核对团队构成、MR 类型/规模、评审负担，并与质量和交付结果并列观察。若要做验证，先采用团队级、带护栏的短周期观察，预先写明复查条件和停止条件。

## 五项 Skill 在这里各自做什么

| Skill | 它会追问的核心问题 |
| --- | --- |
| `metric-decision` | 这个 25% 到底测量了什么，前后是否可比？ |
| `tech-review` | “因此设个人配额”的方案，证据足够吗？ |
| `tech-planning` | 后续应该投资指标治理、团队诊断，还是暂缓配额？ |
| `management-retro` | 这次指标争议暴露了工作系统中的什么可复用问题？ |
| `eng-reporting` | 如何把暂定结论和下一步压缩给需要拍板的人？ |

关键区别是：它们不替组织决定“最终一定不能设目标”，而是把当前证据支持到哪里、还缺什么、下一步如何验证说清楚。
