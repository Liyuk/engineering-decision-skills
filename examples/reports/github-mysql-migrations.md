# 案例报告：GitHub 的在线 MySQL 迁移工作，五种技术管理输出

- **适合谁看：**正在评审数据库迁移提案或规划数据库平台投资的技术经理、工程经理和资深 Tech Lead。
- **材料：**GitHub 2016 年关于 gh-ost 的一手说明，以及 2020 年关于 schema migration 自动化的工程文章。[gh-ost](https://github.blog/news-insights/company-news/gh-ost-github-s-online-migration-tool-for-mysql/) · [自动化流程](https://github.blog/enterprise-software/automation/automating-mysql-schema-migrations-with-github-actions-and-more/)

## 来源事实与边界

GitHub 在 2016 年称，当时每天会进行多次 MySQL schema 变更，并描述了复制库迁移、MySQL Online DDL 和在线迁移工具之间的运维取舍。文章强调可暂停、可调速、可审计、可在复制库上测试等需求。2020 年文章又描述了 schema 审核、数据库基础设施审批、迁移排队、按集群选择策略、长任务状态沟通和使用 gh-ost 的流程；其中大型表迁移可能持续数小时或数天，同一集群一次只运行一个 ALTER。

这是 GitHub 的历史自述，不是独立基准测试或现状审计。下方的“本团队”没有提供本地表规模、拓扑、流量、版本、成本、人力或故障预算，不能直接照搬 GitHub 的工具选择。

## 五项能力分别会给出的报告

### 1. `tech-planning`：把“买/做哪个工具”改成分阶段投资决策

**结论：**GitHub 的材料支持一种规划理由：高频变更和已有流程的可控性问题，足以让“投资迁移安全与可操作性”进入候选方案；但不足以证明其他团队应直接采用 gh-ost。建议先确认本团队迁移频率、表规模和复制拓扑，再比较原生 DDL、复制库流程和迁移工具；通过代表性复制库测试后，仅对一类低风险变更做试点。

**取舍依据：**比较的不只是执行速度，还包括复制延迟、暂停/限速能力、切换影响、并发与排队、数据核验、运维成本和回退方式。

**待确认：**各方案在本团队负载上的迁移时长、复制延迟、失败率、人工操作时间及维护成本。没有这些数据，不给 ROI 或迁移时长承诺。

### 2. `metric-decision`：公开案例讲了控制能力，没有给可迁移的绩效基线

**结论：**仅凭这两篇文章，不能说 gh-ost 让本团队的迁移“更快”或“更安全”。可先定义用于试点的测量：迁移耗时、复制延迟峰值/超限时长、限速或暂停次数、数据一致性检查结果、人工介入和回退情况。

**口径要求：**按相同表类型、规模、写入率和运行环境比较；记录数据库版本、拓扑、迁移策略和采样窗口。GitHub 所述复制库测试与自身生产实践是其公开经验，不替代本地对照测量。基线与可接受阈值均待确认。

### 3. `tech-review`：直接“全库默认使用 gh-ost”的提案还缺本地验证

**演示送审文本：**“下季度所有 ALTER 都切换到 gh-ost，以统一迁移方式并降低生产风险。”这是为评审而构造的提案句子，不是 GitHub 原文。

| 问题 | 依据 | 影响 | 建议动作 |
| --- | --- | --- | --- |
| “降低风险”没有本地数据支持 | 公开文章描述 GitHub 自己的负载、操作特征和经验 | 无法确认本地是否适配或风险是否真的下降 | 用代表性表与负载做复制库测试，核对数据一致性、复制延迟与资源占用 |
| 没有说明拓扑、二进制日志配置、分片方式与切换策略 | gh-ost 的运行方式取决于服务配置；文章说明分片迁移需逐 shard 处理 | 工具兼容性和切换边界尚未建立 | 先列目标环境矩阵，确认不适用场景和人工审批点 |
| 没有排队、并发、监控、负责人和回退安排 | GitHub 的流程文章指出迁移可能持续数小时/数天，需排队、查运行状态并沟通进度 | 全库切换可能造成资源争用，也可能使长任务无人负责 | 提交按集群执行、运行状态、暂停/回退和迁移后核验设计 |

**评审结论：**当前文本不足以支持“下季度全库默认切换”。可带条件批准兼容性验证和小范围试点；本结论只针对该演示句子，不代表完整方案审查。

### 4. `management-retro`：后续经验显示“工具”之外还需要运营机制

**复盘判断：**对照 GitHub 两篇自述，问题演变不只是“找一个更好的迁移工具”：2016 年材料聚焦迁移过程可控和主库负载风险；2020 年材料进一步描述审批边界、策略选择、队列、集群状态、长任务沟通和逐集群调度。可支持的学习是，工具能力需要与部署职责、排队机制、状态可见性和数据验证一起设计。

**结论边界：**这是对两篇公开文章的时间序列解读；它们没有提供完整事故集、成本趋势或反事实，不能断言自动化单独造成效率提升，也不能确认所有后续设计都由早期痛点直接导致。

**下次验证：**试点后复查迁移任务是否可暂停、状态是否可追踪、并发是否受控、数据是否核验，以及操作人员投入是否变化。若只部署工具而没有运行数据，不应宣称规划目标已达成。

### 5. `eng-reporting`：给管理层的投资决策摘要

> GitHub 的历史案例说明，高频 schema 变更会把复制延迟、迁移可控性、切换和运维负担带入生产风险；后续自动化还需要审批、排队、运行状态和逐集群调度。建议本团队先投入一个有退出条件的兼容性试点，不批准未验证的全库切换。试点需覆盖代表性拓扑和表规模，并报告迁移时长、复制延迟、数据核验及人工介入。当前尚无本地基线、成本或风险阈值，需由数据库与服务负责人补齐后再决定扩大范围。

**与其他能力的区别：**规划输出投资顺序，评审输出是否能批准当前提案，指标输出验证口径，复盘输出从已发生过程学到什么，汇报则把这些已形成的判断压缩给决策者。
